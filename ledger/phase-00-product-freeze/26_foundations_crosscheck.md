## 1. Scope and reading note

This table mechanically cross-checks every frozen Phase 0 convention against the foundations specification. Per AGENTS.md §2, the foundations document governs on conflict.

**Section-numbering caution (recorded to prevent a wrong citation):** foundations §6 ("Domain model and data contracts") ends at §6.4. There is **no foundations §6.5**. The "§6.3 / §6.4 (outbox/inbox)" and "§6.5" references in the ledger's P0.14 and P0.16 report traces are **report** sections (the report's own §6), not foundations sections. Foundations messaging/storage conventions live in §13.2–§13.3 and are cross-checked here against the P0.16 freeze. Similarly, foundations §12.4 is "OT segmentation and control boundary", not the grid-provider table (which is report §12.4; foundations grid-tool roles are §11.1).

## 2. Foundations §6 conventions found (complete enumeration)

§6 contains exactly four subsections; every mandatory convention they carry is listed here and appears in the table in §3:

- **§6.1 Canonical entities** — ten entities with key fields: Portfolio, Site, DER asset, Electrical node/branch, Measurement, Forecast, Schedule, Dispatch command, Execution result, Audit event.
- **§6.2 Units and sign conventions** — MANDATORY CONVENTION box: "FlexCore uses SI-compatible engineering units internally and stores a unit with every external measurement. No implicit unit conversions are allowed at protocol boundaries. The convention below defines positive active power at the POI as export from the site/portfolio to the grid." Table rows: Active power P (MW; positive = injection/export to grid at the POI; consumption is negative net injection); Reactive power Q (MVAr; "Positive/negative direction is explicitly configured to match the network model and device convention; never inferred from sign alone"); Energy E (MWh); Voltage ("kV at nominal base in network model; per-unit in solver representation"); Current ("A or per-unit on explicit base"); Time ("UTC epoch/time plus original timezone metadata where relevant. Simulation time is separate from wall-clock time"); State of charge ("Fraction in [0,1] or percent, but one representation is selected per API and stated explicitly"). There is no frequency row and no apparent-power row in the §6.2 table.
- **§6.3 Asset capability representation** — "Asset models must describe more than nameplate MW"; the capability contract includes operating mode, active/reactive power envelope, apparent-power rating, ramp limits, availability, duration/energy budget, state variables, minimum/maximum state, efficiency/losses, temperature or process limits where relevant, communication state, and vendor/commissioning provenance; minimum model elements per asset class (BESS, Solar PV, Wind, EV charging fleet, Flexible C&I load, Site/microgrid).
- **§6.4 Data quality and freshness** — every measurement MUST carry a quality status: GOOD, SUSPECT, BAD, MISSING, ESTIMATED, or STALE (or a mapped equivalent with consistent semantics); freshness limits are configurable by point type, service, protocol and operating mode — there is no universal stale timeout; clock offset, event-time skew, duplicate sequence, missing intervals, impossible values, range checks and cross-sensor residuals are monitored; bad or stale values are not silently replaced by zeros; estimation/interpolation is explicit, tagged, bounded by policy, and disallowed for safety-critical authorization unless approved; telemetry correction and late arrival must be append-only or versioned so historical decisions can be replayed using the data available at decision time.

Conventions outside §6 that the Phase 0 freeze also rests on (cross-checked here because the ledger's P0.11, P0.12, P0.13, P0.16 and P0.18 depend on them): foundations §3.1 (no hard-coded universal control cadence), §4 principles incl. fail-closed authorization and "simulation, read-only, operator-approved dispatch, and limited automation are distinct deployment modes", §4.1 Deployment modes (four modes with allowed writes), §7.2 (BESS binary decision makes the problem MISOCP, "not a plain continuous SOCP"), §7.6–§7.8 (SOCP exactness not universal; AC power-flow verification checklist; "AC power-flow verification is not AC-OPF"), §9 (command lifecycle figure, §9.1 state definitions, §9.2 command invariants, §9.3, §9.4 timing/acknowledgement policy), §11.1 (grid-tool roles), §12.1/§12.4/§12.6 (security objectives, OT boundary, safety assurance), §13.2–§13.3 (storage table, durable persistence, outbox/inbox), §15.2 (release gates incl. the deployment gate before enabling field writes), §16.1/§17.1 (simulation-first first release; simulation-first assumption).

## 5. Conflicts summary

**Unresolved conflicts: zero.**

- No row in §3 is a Conflict. Where the report and the foundations differ in granularity, the report rule is in every case a stricter or more granular selection that the foundations text permits, or an addition on a topic the foundations does not address.
- **Divergence (a) — SOC representation** (foundations §6.2 vs report §10.2, P0.07 §8): recorded in §3 as a compatible refinement. Resolution: fraction [0,1] at the API boundary is the single selected representation, which foundations §6.2 explicitly permits ("one representation is selected per API and stated explicitly"). If the report were instead to be treated as deviating (it does not — it selects within the permitted space), a deviation ADR would be required; none is needed.
- **Divergence (b) — CANCELLED/SUPERSEDED** (foundations §9.1 merged row vs report §14.2 / P0.11 §3.1): recorded in §3 as a compatible refinement. Resolution: the states remain distinct and separately audited; the foundations merged row describes both causes ("authorized cancellation or newer schedule revision") and does not forbid distinguishing them. If the report were to be followed as a deviation (it does not need to be — the foundations row permits the distinction), a deviation ADR would be required; none is needed.
- **Naming note — "Read-only integration" (foundations §4.1) vs "read-only / shadow mode" (report §21.4, P0.18):** same mode and same write boundary; the report term is a refinement, recorded here so it is not left implicit. No ADR required.
- Per ledger P0.26 step 3, had any conflict been found, the resolution would be in favour of the foundations document, with a deviation ADR only if the report were to be followed instead. No such case arose.
