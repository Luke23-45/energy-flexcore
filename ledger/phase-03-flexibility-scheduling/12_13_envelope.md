## 1. Decisions recorded here

| # | Decision | Where implemented |
|---|---|---|
| D-P3.12-1 | **Constrained aggregation, decided once:** per interval, `P_portfolio(t) = Σ_i P_net(i,t) − P_loss/adjustment(t)` is composed in a fixed order: (1) the frozen P3.02 narrowing of each asset's declared P_net range (reused `narrow_interval`; UNKNOWN → collapse-to-zero credit; empty intersection → the interval is INFEASIBLE, never widened back); (2) the per-interval forecast cap through the P3.31 labelled accessor ONLY (PV: upper bound = forecast × availability; load: baseline + declared offsets); (3) availability scaling toward zero, with no evidenced availability crediting NOTHING (recorded narrowing); (4) the conservative horizon-start energy cap for BESS (usable energy above the floor / headroom below the ceiling over one interval, NO intra-horizon recharge/discharge credit; REQUIRED for BESS-class dispatchable assets — omitting it is a named error); (5) the shared site PCC export/import caps applied to the site SUM (the coupling binds the aggregate, §11.6); (6) the loss/adjustment term subtracted. The output is per-interval lower/upper bounds plus the central estimate (the recorded midpoint convention). | `flexibility_envelope.rs` (`calculate_portfolio_envelope`) |
| D-P3.12-2 | **Correlation treatment, decided once (ledger open question 4):** (a) forecast-driven assets are bounded per interval by their per-asset forecast from the single labelled fixture, so a shared weather driver enters through the forecast VALUES, not through an assumed statistical correlation — no derating is added on the forecast-capped contribution; (b) assets DECLARED into a `SharedExposureGroup` carry a CONFIGURED conservative derate fraction in [0, 1] with a MANDATORY recorded basis string (labelled ASSUMPTION); both bounds of every member's range are scaled by (1 − f) toward zero before the site aggregation; (c) assets in NO group are listed in `CorrelationTreatmentRecord::unmodelled_assets` — no correlation model on record, none assumed. NO correlation coefficient is ever generated by the module; the statement is carried verbatim on every envelope (`CORRELATION_TREATMENT_STATEMENT`). Shared communication-path constraints: no data, recorded unknown dimension. The derate is a whole-group scalar; a per-asset-class divergence is a future recorded decision, not a silent extension. | `flexibility_envelope.rs` (`SharedExposureGroup`, `validate_groups`, `asset_range_at`) |
| D-P3.12-3 | **Confidence: explicitly NOT supported.** None of the P3.05–P3.11 models provides a verified confidence or availability distribution, so every envelope carries the constant `AVAILABILITY_DESCRIPTOR_NOT_SUPPORTED`; no confidence number is invented anywhere. The central estimate is the recorded midpoint of the per-interval feasible range and carries NO confidence number. | `flexibility_envelope.rs` (module header, descriptor constant) |
| D-P3.12-4 | **Loss/adjustment term (§11.6):** no loss model exists in the registry/scenario. `LossAdjustment::Unmodelled` applies 0.0 and records `LossAdjustmentUnmodelled` (omitting losses may overstate export capability — stated, never hidden; no value invented — the D-P3.05-2 honesty precedent). A declared constant with UNKNOWN provenance is NOT credited (recorded, unknown never widens). | `flexibility_envelope.rs` (`LossAdjustment`) |
| D-P3.12-5 | **Site coupling and the registry gaps:** the P2.02 site entity carries the PCC and grid model as REFERENCE strings only; the numeric export/import limits are REQUIRED configuration (gap G17). Site limits follow the P3.02 rule: UNKNOWN-provenance limit → collapse to zero headroom (tested). The envelope consumes the fixture on the fixture's own grid (D-FX-1); a mismatched grid is a named error, never an implicit aggregation. The envelope is ACTIVE-POWER only (the §11.6 formula); no reactive envelope is composed and the per-asset Q capability (P3.08/P3.09, zero volt-var credit) is recorded as an unknown dimension. | D-P3.12-6 | **Envelope-input labelling place (four-place rule, D-FX-8):** the envelope's `EnvelopeInputSnapshot` carries the fixture id, the forecast VERSION, and the SYNTHETIC provenance label; forecast values are read only through `LabeledSeriesValues` (label + version + quantity travel on every read), and the caller obtains the fixture through `validate_forecast_input` (place 3). | D-P3.13-1 | **Trigger set and semantics, decided once:** `TelemetryQualityChanged` → stale when the asset is in the envelope's scope and the tenant matches (ANY quality transition invalidates, in either direction — the recorded computation's input basis changed; §10.4's non-silencing rule applies to improvements too); `AssetAvailabilityChanged` and `AssetCapabilityUpdated` → stale for a scoped, same-tenant asset; `ForecastPublished` → stale when the published forecast version differs from the envelope's input-snapshot version (the SAME version dedupes; per D-FX-9 the caller reads the version from the fixture store via the event's scope); horizon rollover → stale when the new horizon start lies at or beyond the envelope's end-exclusive horizon end; maximum age → stale when `now − computed_at > max_age` (age == limit NOT stale — the P2.08 convention; a clock read before the computation is not stale). A foreign-tenant event never invalidates (P0.16 rule 5). All rules are the pure `evaluate_envelope_trigger` / `evaluate_max_age`. | `envelope_staleness.rs` (module header, trigger table) |
| D-P3.13-2 | **Envelope metadata and schedule reference:** every envelope carries `EnvelopeMetadata` (version, computation timestamp, input-snapshot reference, forecast version, horizon bounds, sorted scoped assets); schedules reference the envelope version they used through `ScheduleEnvelopeReference` (exposed for P3.21), gated by `check_schedule_envelope_reference` (a non-current version is `EnvelopeSuperseded` — rejected or re-derived) and `assert_usable_for_new_schedule` (stale → `StaleEnvelopeRejected`; recompute or fail loudly, never silently proceed). The enforcement wiring into the schedule store and lifecycle lands in P3.22/P3.24; the checks here are pure. | `envelope_staleness.rs` |
| D-P3.13-3 | **Maximum age bound: configuration with a recorded default** — `StalenessConfig::max_age_millis`, default `DEFAULT_MAX_AGE_MILLIS` = 3 600 000 ms (one hour). A configuration default, not a report requirement. | `envelope_staleness.rs` |
| D-P3.13-4 | **Debouncing (the ledger performance risk), recorded as CONFIGURATION:** `StalenessConfig::min_recompute_interval_millis` (default 0 = no debounce) turns a triggered recomputation ADVICE from `Immediate` into `Deferred { not_before }` while the window is open. **The guarantee debounce cannot weaken (recorded invariant, tested directly):** debounce applies ONLY to the advice; it never changes `EnvelopeFreshness`, and both hard gates (`assert_usable_for_new_schedule`, `check_schedule_envelope_reference`) do not even take the debounce configuration as an argument. A deferred recompute leaves the envelope STALE until recomputation completes — the scheduler still recomputes-or-fails, just not necessarily instantly. | `envelope_staleness.rs` (`DEBOUNCE_GUARANTEE_STATEMENT`, `the_debounce_cannot_weaken_the_staleness_guarantee`) |

## 2. Gaps and limitations (recorded, none silently filled)

- **Event payload gap** (D-P3.12-7): `FlexibilityEnvelopeUpdated` cannot
  carry the version/horizon/snapshot on the wire until flexcore-events adds
  them additively; the nil-asset-id convention and the version-carrying
  idempotency key are the interim recorded path.
- **No registry capability version** (the P3.01–P3.11 survey gap): the
  registry's `capability_profile` is an unversioned reference string, so the
  input snapshot records the reference strings per asset — a versioned
  capability snapshot requires the Phase 2 registry to version the profile
  reference (recorded as a downstream need, not rebuilt here).
- **Time coupling is conservative, not solved** (D-P3.12-1 step 4): the
  envelope applies the horizon-start energy cap and takes NO intra-horizon
  recharge credit; the full cross-interval MILP formulation is P3.17's
  concern. For EV fleets without an energy cap, the per-interval range
  ignores connection windows and the hard departure constraint
  (D-P3.11-2) — recorded as `EvEnergyCouplingAbsent` on every such
  envelope.
- **Active-power only** (D-P3.12-5): no reactive envelope is composed; the
  §11.6 formula is P-only and no reactive data exists in the scenario.
- **Load availability semantics:** availability scales the flexibility
  OFFSETS toward zero while the forecast baseline persists (an unavailable
  load still draws its baseline) — the recorded convention for this
  calculator.
- **Debouncing is advice-only** (D-P3.13-4): the runtime recompute loop
  that consumes `RecomputationAdvice` lands with the scheduler wiring
  (P3.21/P3.22); until then the advice is a pure value.
