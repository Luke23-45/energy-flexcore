## 1. Decisions made once

| ID | Decision | Rationale | Alternative considered and rejected |
|---|---|---|---|
| D-S1 | All primary keys are **UUIDv7, generated by PostgreSQL 18's built-in `uuidv7()`** (`DEFAULT uuidv7()`) | RFC 9562 time-ordered UUIDs keep B-tree index inserts locality-ordered, avoiding the random-insert fragmentation and buffer-cache churn of UUIDv4; `uuidv7()` is native in PostgreSQL 18 with no extension (`RESEARCH.md` §6), and the Phase 1 pin is PostgreSQL 18 | UUIDv4 (`uuidv4()` / `gen_random_uuid()`): rejected because fully random keys scatter inserts across the index; no confidentiality benefit is claimed either way — these are internal identifiers, not secrets. Caveats recorded in §2.3 |
| D-S2 | **`asset_state` is included** as a current-state table (one row per asset, updated in place) | The exit-gate workflow (P1.26) verifies each §10.1 entity in PostgreSQL; `AssetState` is a §10.1 canonical entity already implemented as a domain type in P1.06; registration records initial availability/operating mode, and Phase 2 telemetry needs a current-state row to update in place per §6.5 — omitting it would force a schema change under Phase 2 telemetry code. Its quality column is also the reuse site for the P0.08 enum created now (CONTEXT.md: "Phase 1 stores the enum") | Deferred to Phase 2: rejected (reason above). Asset-state *history* is NOT created here — it is Phase 2 (time-series, §8) |
| D-S3 | **No retention values anywhere in the schema** (P0.16 §4; §16.3) | Retention is configurable per data class by customer contract, regional market rules, and privacy/security requirements; a value in DDL or a partition-drop schedule would be a universal retention period in code | Hard-coded defaults "for dev convenience": rejected; the Compose stack (P1.25) may set dev-only configuration values outside the schema, marked dev-only |
| D-S4 | Quality is a **PostgreSQL enum type with exactly the six P0.08 values**, created in Phase 1 | The enum is created now for reuse (CONTEXT.md) and is used immediately by `asset_state.quality`; an enum structurally rejects a seventh value at the database (P1.13 test) | `text` + CHECK constraint: rejected — an enum cannot gain a value without an explicit `ALTER TYPE` migration, which is the stronger guarantee for a frozen vocabulary |
| D-S5 | SOC lives **only in state/profile tables, never on `assets`** | SOC is a per-asset *state* (P0.10 §1 AssetState row), not an asset attribute; the `CHECK (soc >= 0 AND soc <= 1)` constraint is applied on `asset_state` now and repeated on every future SOC column (telemetry, asset profiles in Phase 2+) as a forward constraint (P0.07) | Storing a "current SOC" on `assets`: rejected — conflates identity with state and invites a second source of truth |

## 2. Scope and shared conventions

### 2.1 Stage 1 tables — exactly these, and no others

| Table | Purpose | Tenant-owned | §6.5 storage strategy |
|---|---|---|---|
| `tenants` | Tenant registry root | No (it *is* the tenant root) | Current-state table |
| `portfolios` | Portfolio registry | Yes | Current-state table |
| `sites` | Site registry | Yes | Current-state table |
| `assets` | Asset registry | Yes | Current-state table |
| `asset_state` | Current state per asset (D-S2) | Yes | Current-state table (history is Phase 2) |
| `outbox` | Transactional outbox (§6.3, §15.5) | No (infrastructure queue; §5.6) | Append-oriented working queue; drained to JetStream, then retained until operational cleanup |
| `audit_records` | Append-only audit evidence (§10.1) | Yes | Append-oriented event history (§6.5 bullet 1) |

Explicitly **not** in the Stage 1 design (each is a named failure mode in the ledger):

- **No telemetry tables** — raw/normalized telemetry, partitions, and time-series storage are Phase 2 (§16.1 row 2); creating them here guarantees a redesign (ledger P1.12 risk note).
- **No scheduling, grid-model, forecast, command, approval, market, plugin, or user/membership tables** — the corresponding §10.1 entities (Schedule, DispatchCommand, GridModel, ForecastBundle, PluginInstance, MarketCommitment) have no Phase 1 writer; §16.1 assigns them to PostgreSQL in general, not to Stage 1. The command lifecycle exists in Phase 1 as a domain type only (P1.06); there is no dispatch path and therefore no command table.
- No `users`/`roles` table: identity is external (OIDC); `tenants.idp_reference` (§10.1) is the only identity field in Stage 1.

### 2.2 Conventions applied to every table

- All timestamps are `timestamptz`; canonical storage is UTC (P0.09 §2). Local time is never stored; `sites.timezone` carries the IANA site timezone separately.
- `event_time` / `ingest_time` are distinct columns and never merged or substituted (P0.09 §1), on every table that carries domain time: `asset_state` and `audit_records` (§5.5, §5.7). The `outbox` row is a *delivery* record: the wrapped event's `event_time` lives in `payload.event_time` (P1.09), and `created_at`/`updated_at` are the delivery-lifecycle times — recorded so P0.09's distinction is not silently lost.
- `tenant_id` is `NOT NULL` and part of every tenant-owned row and query scope (P0.16 rule 1; §16.2).
- Money-free, unit-bearing numeric columns use canonical units at the API boundary (P0.07): MW, MVAr, MWh as `double precision` matching the Rust `f64` contract types (P1.05); SOC is a fraction in [0,1] (D-S5).
- No column stores a percentage representation of SOC; percentage conversion happens at the adapter (P0.07).

### 2.3 UUIDv7 caveats recorded with D-S1

- `uuidv7()` embeds a millisecond timestamp; it is not strictly monotonic across concurrent transactions. Uniqueness is guaranteed; *ordering by UUID is approximate* and never used as business ordering — ordering uses `event_time`/`ingest_time` and source sequence (P0.09), never `ORDER BY id`.
- `uuid_extract_timestamp()` is available for diagnostics (PostgreSQL 18, `RESEARCH.md` §6).
- Portability note: `uuidv7()` is PostgreSQL 18+; the Phase 1 pin is PostgreSQL 18 (18.6 latest minor at the cut-off, `RESEARCH.md` §6). Downgrading the server major without a recorded pin change would break defaults — this is a pin discipline item, not a schema alternative.

## 3. Shared database objects

### 3.1 Roles (created by deployment bootstrap, not by migrations)

| Role | Purpose | Privileges |
|---|---|---|
| `flexcore_migrator` | Owns all tables; runs `sqlx migrate` (P1.13 step 2, P1.25 migrate step). Never used by the application at runtime | `CREATEROLE`-granted by bootstrap; table `OWNER`; runs DDL |
| `flexcore_app` | Application runtime role (control plane + worker). **Never the table owner** (§16.2 rule 3; [R25] caveat) | `SELECT`, `INSERT`, `UPDATE` on registry/state/outbox tables; `SELECT`, `INSERT` on `audit_records`; **no `DELETE`, no `TRUNCATE`, no DDL anywhere** (§6) |

`CREATE ROLE` needs privileges the migrator may not carry; roles are therefore a bootstrap/deployment step (Compose init or equivalent), and migrations create tables and grants only. Recorded so P1.13 does not try to `CREATE ROLE` inside a migration.

### 3.2 Quality enum (migration 0001)

```sql
CREATE TYPE telemetry_quality AS ENUM
  ('GOOD', 'SUSPECT', 'BAD', 'MISSING', 'ESTIMATED', 'STALE');
```

- Exactly the six P0.08 canonical states, in P0.08 §1 order (enum order is fixed at creation; comparison order follows it).
- A seventh state cannot be inserted — the database rejects it (P1.13 acceptance test). P0.08 §3 source-state mapping (e.g. `SUBSTITUTED`, `OUT_OF_RANGE`) happens at the adapter; the original source code travels as diagnostic metadata in payloads, never as a new enum value.
- Evolution rule: adding a value requires an explicit `ALTER TYPE ... ADD VALUE` migration and a Phase 0-deviation ADR, because the canonical vocabulary does not grow (P0.08 §1); values are never removed or reordered.

Indexes: `(tenant_id, event_time)`; `(object_type, object_id)`.

**Append-only enforcement (three layers, all recorded):**

1. **Grants:** `flexcore_app` receives `INSERT`, `SELECT` only. `REVOKE UPDATE, DELETE, TRUNCATE ON audit_records FROM PUBLIC` and no `UPDATE`/`DELETE` grant to **any** role, including future ones (grant reviews must keep it that way).
2. **Defence-in-depth trigger:** a `BEFORE UPDATE OR DELETE` trigger on `audit_records` raises an exception unconditionally — including for the table owner, whose owner privileges grants cannot revoke. Dropping the trigger is itself a migration-level, git-audited act.
3. **Domain rule:** the P1.10 audit port exposes append only; no update/delete method exists at any layer.

The `flexcore_migrator` owner retains nominal owner rights (unavoidable); layer 2 is what closes that gap. This is stated so no one mistakes grant revocation alone for owner-proof append-only storage.

## 5. Row-Level Security design (§16.2, P0.16 §2–§3)

### 5.1 Mechanism

- Tenant context per transaction: the application sets `SET LOCAL flexcore.tenant_id = '<uuid>'` on every transaction, derived only from authenticated claims (P0.16 rule 5; P1.13 step 3 implements this at the connection level; a query without a tenant context fails).
- One policy per tenant-owned table, `FOR ALL`, deny-by-default:

```sql
CREATE POLICY tenant_isolation ON <table>
  USING      (tenant_id = NULLIF(current_setting('flexcore.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('flexcore.tenant_id', true), '')::uuid);
```

An unset/empty setting yields `NULL` → the predicate is `NULL` → **zero rows and no writes**. A missing tenant context fails closed, never open.

- `ENABLE ROW LEVEL SECURITY` **and** `FORCE ROW LEVEL SECURITY` on every tenant-owned table. `FORCE` exists precisely because owners otherwise bypass policies ([R25]; P0.16 §3).

### 5.2 RLS coverage matrix (every table's policy is specified)

| Table | `tenant_id` | RLS enabled + forced | Policy | Rationale |
|---|---|---|---|---|
| `tenants` | n/a | No | None | The table *is* the tenant root; there is no per-tenant row filter to express in Phase 1 (no membership table exists). Access is application-authorized; Phase 2 user/membership tables will carry RLS |
| `portfolios` | `NOT NULL` | Yes | `tenant_isolation` (§5.1) | Tenant-owned |
| `sites` | `NOT NULL` | Yes | `tenant_isolation` | Tenant-owned |
| `assets` | `NOT NULL` | Yes | `tenant_isolation` | Tenant-owned |
| `asset_state` | `NOT NULL` | Yes | `tenant_isolation` | Tenant-owned |
| `outbox` | none | No | None | Infrastructure queue, not tenant-owned (§4.6); reachable only by `flexcore_app`; payload carries tenant attribution |
| `audit_records` | nullable | Yes | `tenant_isolation` | Tenant-owned; rows with `tenant_id IS NULL` (platform-level) are invisible to `flexcore_app` under the policy — platform records are readable only through the owner/ops path |

### 5.3 [R25] table-owner caveat — stated and operationalised

PostgreSQL RLS can restrict rows per user/policy, but table owners typically bypass policies unless configured otherwise; do not rely on a policy while running the application as the table owner (§16.2 [R25]). Consequences, all binding on P1.13:

- `flexcore_app` is **never** the table owner and never connects with owner credentials (P0.16 rule 3).
- `flexcore_migrator` owns the tables and runs only migrations; runtime traffic never uses it.
- `FORCE ROW LEVEL SECURITY` is applied on all five tenant-owned tables, so even owner-role sessions are subject to the policies while the `FORCE` flag stands.
- P0.16 rule 2.4 requires testing *all* service roles, including owners: P1.13's RLS tests run the isolation cases for the runtime role and the migrator role, and P1.23 re-tests every service role the deployment defines.
- Cross-tenant access denials are audited (§16.2 rule 6): the application writes an `audit_records` row for each denial — RLS itself denies silently, so the audit duty sits in the application/authz layer (P1.11).

## 6. Privilege model summary

| Table | `flexcore_app` | `flexcore_migrator` |
|---|---|---|
| `tenants`, `portfolios`, `sites`, `assets`, `asset_state`, `outbox` | `SELECT`, `INSERT`, `UPDATE` (RLS applies) | `ALL` (owner; migrations only) |
| `audit_records` | `SELECT`, `INSERT` only | `ALL` (owner; migrations only; append-only trigger still blocks `UPDATE`/`DELETE`) |

No role holds `DELETE` or `TRUNCATE` on any Stage 1 table via grants (registry tables simply have no Phase 1 delete path; if a future phase needs deletes it must add them by an explicit, reviewed migration). `flexcore_app` has no DDL privilege.

## 7. Migration discipline

- **Runner:** `sqlx migrate` (SQLx 0.9.0 + `sqlx-cli` 0.9.0; offline mode always enabled in 0.9 — `RESEARCH.md` §4). Migration files live with the Postgres adapter (`crates/adapters/postgres/migrations/`, P1.13).
- **Numbering:** sequential zero-padded version numbers (`0001_quality_enum`, `0002_tenants`, …); numbers are never reused; applied migrations are never edited — a correction is a new migration.
- **Forward-only semantics:** the schema only moves forward in every real environment. Down files exist for dev/CI rollback of the most recent migration, not for production time travel.
- **Up + down (or recorded irreversible):** every migration has an up file and a `<version>_<description>.down.sql`. Where a down migration is genuinely irreversible (e.g. dropping a column that carried data), the down file contains only a comment `-- irreversible: <reason>` and the reason is reviewed with the migration — never an empty file and never a missing one.
- **Content per migration:** DDL + grants + RLS statements for exactly the objects it creates; the enum (0001) precedes every consumer of it.
- **CI:** migrations run against a real PostgreSQL 18 service in CI (P1.27), including up from empty, down of the latest step, and re-up — mirroring the P1.13 acceptance check ("migrations run up and down cleanly from an empty database"). The testcontainers-vs-CI-service harness choice is P1.13's open decision (CONTEXT.md open question 5); this document only fixes that it must be a real PostgreSQL 18.
- **Ordering guarantee:** RLS and grants are part of the same migration as their table, so no migration leaves a tenant table momentarily without its policy.

Indicative migration list (P1.13 may split further but not merge away the discipline): `0001_quality_enum`; `0002_tenants`; `0003_portfolios`; `0004_sites`; `0005_assets`; `0006_asset_state`; `0007_outbox`; `0008_audit_records` (incl. append-only trigger).

## 8. §6.5 storage-strategy mapping

| §6.5 strategy | Applies to (Stage 1) | Future |
|---|---|---|
| Current-state tables | `tenants`, `portfolios`, `sites`, `assets`, `asset_state` (updated in place; one row per entity) | Schedules, configuration, portfolio state (later phases) |
| Append-oriented event history | `audit_records` (command lifecycle, approvals, plugin/configuration/security actions accrue here from their phases onward) | Command/audit evidence tables per §6.5 bullet 1 |
| Transactional outbox (§6.3) | `outbox` — a working queue, drained to JetStream (§16.1 row 5: JetStream is messaging, never the authoritative business database) | — |
| Time-series tables | **None in Stage 1** — telemetry tables are Phase 2, with declarative partitioning per `RESEARCH.md` §6 | Telemetry and measurements |
| Object storage | None in Phase 1 | Simulation artifacts, reports, model files, exports (§6.5 bullet 4) |

The §6.5 closing rule holds by construction: no single append-only event log is the source of truth for high-volume telemetry, because no telemetry storage exists in this phase and none is designed here.

## 9. Retention (D-S3)

No retention value, default period, or per-class duration appears in this design, in any DDL, in any index or trigger, or in any future partition scheme created from it (P0.16 §4; §16.3). The seven §16.3 data classes map to storage that arrives in later phases (telemetry partitions: Phase 2; command/audit evidence: this `audit_records` design plus later evidence tables). Retention is configuration owned by deployment/operations, never schema.
