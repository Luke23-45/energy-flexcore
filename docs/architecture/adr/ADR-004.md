## Context

§7.2 allocates Python to power-system simulation adapters, numerical research, optimization experimentation, ML/GNN/MARL workers, forecasting, and benchmark pipelines, because the mature scientific and power-system ecosystems (pandapower, GridLAB-D, OpenDSS bindings, solver stacks) live there — while explicitly forbidding a second general-purpose backend in Python: "Rust remains the source of truth for command authority and domain workflows." §8.3 requires the Python numerical/ML workers to be separate processes because of native dependencies and resource isolation; §5.4 Class C makes them out-of-process gRPC/Protobuf workers that isolate Python dependencies, crashes, CPU/GPU load, and research packages from the Rust control-plane runtime. §8.2 adds that research workers communicate through Protobuf/gRPC or scenario artifacts and do not import internal database tables.

Evidence: ledger/phase-00-product-freeze/19_plugin_model.md (P0.19 §5, Class C) freezes the out-of-process worker execution class; ledger/phase-00-product-freeze/20_deployment_build_form.md (P0.20 §5) freezes the worker build form (Linux Python container images pinned by lockfile).

## Decision

Python is confined to scientific, numerical, and research workloads running as out-of-process gRPC/Protobuf workers (§5.4 Class C), deployed as lockfile-pinned Linux containers. Python is never a second general-purpose backend: it holds no command authority, owns no domain workflow, and does not import internal database tables; it communicates only via Protobuf/gRPC contracts or scenario artifacts.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Python as a second general-purpose backend (business logic, API, scheduling in Python) | Explicitly rejected by §7.2; it would split command authority across two runtimes and duplicate the domain model. |
| Reimplementing the numerical/power-system stack in Rust | Would abandon the mature scientific and power-system ecosystems that are the reason Python exists in the stack at all (§7.2 rationale), and would force rewriting rapidly evolving research code (GNN/MARL, §13) in a language with far thinner ecosystems there. |
| Embedding Python in the control-plane process (in-process bindings) | Contradicts §8.3 (separate because of native dependencies and resource isolation) and §5.4 Class C: in-process embedding couples crashes, dependency conflicts, GIL/scheduling behaviour, and CPU/GPU load directly into the authoritative control plane. |

## Consequences

**Positive.** Full access to the scientific/power-system ecosystem where it matters; crashes, dependency churn, and heavy compute in research workers cannot take down the control plane; worker versions are pinned and deployed independently; the contract-first boundary (Protobuf) keeps worker internals replaceable.

**Negative.** A serialization/process boundary on every worker call (latency, schema versioning, deployment coordination across two runtimes); duplicate observability and packaging pipelines; contract evolution discipline (Buf checks, §10.5) is mandatory.

**Constrains later phases.** No Python code in the control plane, edge agent, or plugin host process; research workers never write internal tables directly (§8.2); ML/RL worker outputs are proposals only (ADR-010); the feasibility gate may call a Python power-flow worker, but the gate decision itself stays in protected platform code (§12.5; ADR-009).

## Revisit conditions

- A worker whose latency or operational profile cannot tolerate the process boundary would need a case-by-case approved design decision (still not in-process embedding by default).
- §25.1's language revisit triggers (Rust depth, missing protocol bindings) apply to the control-plane language, not to this isolation rule; the isolation itself is revisited only via a new ADR.
