## Context

The site edge crosses the enterprise IT/OT boundary. §3.3 places the edge agent in a customer integration/DMZ position; §17.2 defines five security zones and requires that only documented flows cross zones, with no direct database, NATS, or arbitrary plugin network access from a field-device network; §17.4 treats OT lateral movement as a named threat whose controls are zone/DMZ boundaries, an outbound-only edge connection, and no direct cloud-to-device access. §18.1–§18.2 define edge responsibilities (local communication, buffering, forwarding) and the edge trust boundary: an edge agent is not trusted merely because it belongs to the customer site — it must authenticate each central session and validate every command, and the central platform must not assume an issued command was applied until it receives device/site acknowledgement and telemetry evidence. §8.3 and §21.4 make the edge agent a separately built and distributed artifact (Linux container or systemd service, signed updates) precisely because it needs independent lifecycle at the OT boundary.

Evidence: ledger/phase-00-product-freeze/17_threat_model.md (P0.17) freezes the zone model, the inter-zone flow rule, and the outbound-only topology; ledger/phase-00-product-freeze/20_deployment_build_form.md (P0.20) freezes the edge agent's separate build/distribution form.

## Decision

The site edge agent is a separate deployment and a security boundary: it runs at the site or in the OT DMZ with its own lifecycle and signed updates, connects to the central platform over an outbound-only mTLS channel initiated from the customer side (or through a customer-controlled broker/gateway), and carries approved commands and telemetry only. No inbound internet access into OT networks. The edge authenticates every central session and validates every command; the central platform treats acknowledgement as receipt at the application layer, not physical delivery (§18.2; §14).

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Fold edge connectivity into the central control plane (one deployment reaching into site networks) | Contradicts the §17.2 inter-zone flow rule and the §17.4 OT-lateral-movement controls; P0.17 records that a zone diagram permitting cloud-to-device access contradicts the freeze. It would also defeat the independent edge lifecycle that §8.3 requires. |
| An autonomous edge that makes dispatch decisions at the site | The command lifecycle and final dispatch authority are protected platform invariants owned by the kernel (§0.2; §5.7); §18.1 scopes the edge to local communication, buffering, and enforcing locally configured limits — not to dispatch authority. A second control plane would double the authority surface without adding a gate. |
| Inbound, cloud-initiated connections to site devices as the default pattern | Excluded by §3.3 and §17.4 (avoid inbound internet access into OT networks); a customer security architecture may require a DMZ, unidirectional gateway, or other approved pattern — the outbound-only rule is the invariant, the exact traversal pattern is per-site. |

## Consequences

**Positive.** The OT boundary is respected by construction; D6's per-site cyber/OT review has a concrete, narrow surface to review; the central-outage rule (§21.2: a central outage must not disable site-local protective controls or force an unsafe device state) is supportable because the edge degrades to local buffering and site-local behavior.

**Negative.** A second artifact to build, upgrade, monitor, and secure across heterogeneous sites; per-site integration work (network paths, customer security patterns) is unavoidable; debugging spans two trust domains.

**Constrains later phases.** Edge identities are scoped to one tenant and an approved site/asset set (§16.2 rule 7); the edge agent cannot select a control-authority mode (§21.4; P0.18); the first protocol integration is selected at D5 (OPEN) before v0.4.0; no edge feature may open inbound paths into OT networks.

## Revisit conditions

- A D6 site review that documents a customer security architecture incompatible with the outbound-only pattern would require a recorded, approved deviation for that site — not a silent change to this ADR.
- A material change to the §17.2 zone model (approved design decision) would trigger re-examination.
