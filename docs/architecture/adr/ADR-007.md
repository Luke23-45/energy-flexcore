## Context

§16.1 assigns PostgreSQL the role of primary transactional source of truth (tenants, users/roles references, sites, assets, grid metadata, schedules, commands, approvals, plugins, outbox, audit metadata) with partitioned telemetry tables as the initial telemetry store ("start here; measure before adding a separate analytics database"), and assigns NATS JetStream the role of durable event/work stream — "Messaging, not the authoritative business database." §6.5 prescribes selective event sourcing (append-oriented history for command lifecycle, approvals, plugin/config/security changes; current-state tables for assets, schedules, configuration, portfolio state; time-series tables for telemetry) and forbids using a single append-only event log as the only source of truth for all high-volume telemetry. §6.3 and §15.5 define the transactional outbox for state-change-plus-publish, and §15.4 fixes delivery semantics: JetStream is at-least-once; consumers must be idempotent; exactly-once side effects are never promised from broker features alone ([R6]).

Evidence: ledger/phase-00-product-freeze/16_tenancy_storage_principles.md (P0.16) freezes all six §16.1 storage rows, the seven §16.2 tenancy rules (including the RLS table-owner caveat [R25]), and the no-universal-retention rule.

## Decision

PostgreSQL is the transactional source of truth for all authoritative business state, including command lifecycle, approvals, and audit metadata; telemetry starts in partitioned PostgreSQL tables. NATS JetStream is the durable event and work transport (at-least-once delivery, replay, idempotent consumers) and is never the authoritative business database. Consistency between state and events is maintained via the transactional outbox (§15.5).

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| JetStream (or an event log) as the system of record | §16.1 row 5: JetStream is messaging, not the authoritative business database; §6.5 forbids a single append-only event log as the only source of truth for high-volume telemetry. Broker retention would govern business facts — wrong durability, consistency, and query model. |
| A dedicated time-series database from day one | §16.1: start with partitioned PostgreSQL telemetry tables and measure before adding a separate analytics database; §25.1 carries the revisit trigger (measured telemetry volume requires a dedicated time-series store). Premature infrastructure adds operational surface without evidence. |
| Full event sourcing for every aggregate | §6.5 prescribes selective event sourcing: current-state tables for assets, schedules, configuration, and portfolio state; full event sourcing of high-volume telemetry is explicitly ruled out. |

## Consequences

**Positive.** Transactional integrity for the state that matters most (commands, approvals, authorization evidence); one mature engine with constraints, migrations, and RLS for tenancy defence in depth (§16.2); the outbox gives reliable state-to-event consistency without dual-write anomalies.

**Negative.** The partitioned-tables approach has a real scaling ceiling — a dedicated time-series store will eventually be needed; JetStream still requires per-stream retention/replication/acknowledgement policy (§15.4); at-least-once semantics push idempotency onto every consumer.

**Constrains later phases.** Every tenant-owned table carries `tenant_id` and the §16.2 rules apply (application authz plus RLS; the runtime role must not own tenant tables or bypass RLS; `FORCE ROW LEVEL SECURITY` where appropriate); retention is configured per data class and per contract — no universal retention period in code (§16.3); TimescaleDB stays optional and never mandatory for the open baseline; Redis is not introduced in v0.1.0 unless measurements justify it.

## Revisit conditions

- §25.1 trigger for PostgreSQL: measured telemetry volume requires a dedicated time-series store (adding a TSDB does not move the source of truth).
- §25.1 trigger for NATS JetStream: operational burden or delivery semantics do not fit a target deployment (would require a new ADR for the transport role).
