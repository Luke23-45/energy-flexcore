## Context

§6.1 recommends DDD plus hexagonal (ports and adapters) inside a **modular monolith**: one deployable for the central control plane with strict crate/module boundaries. §8.3 sets the service-extraction policy — keep the first control plane as a modular monolith and separate only the site edge agent, Python numerical/ML workers, the WASM plugin host, and (if measured need appears) a background worker; do not split Portfolio, Asset Registry, Scheduling, and Dispatch into separate network microservices before there is a measured need. §7.1 recommends Rust for the control-plane core (compile-time memory and thread safety, explicit error handling, strong state-machine typing, one backend language across control plane and edge) as a provisional choice with explicit revisit triggers (§25.1). §8.1 defines the target crate layout and §8.2 the dependency rules (domain depends on nothing infrastructure; adapters depend on ports; apps are composition roots).

Evidence: ledger/phase-00-product-freeze/20_deployment_build_form.md (P0.20) freezes the deployment/build form — control plane as a single Linux OCI image plus native binary — consistent with one central deployable.

## Decision

The central control plane is built initially as a single Rust deployable (modular monolith) with strict internal crate boundaries per §8.1–§8.2. Rust is the provisional implementation language per §7.1 and §25.1. Services are extracted only per the §8.3 policy, when a measured need for scaling, isolation, release cadence, or fault containment exists.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Start with microservices for the core domains | §6.1: "Do not begin with dozens of microservices"; §8.3 forbids splitting Portfolio, Asset Registry, Scheduling, and Dispatch into separate network microservices before a measured need. Early distribution would trade transactional simplicity (§6.3) for an operational burden the 0.x line cannot justify. |
| A second general-purpose backend in Python (or another dynamic language) | §7.2 explicitly: "Do not create a second general-purpose backend in Python." Python is isolated to numerical/research workers (ADR-004); command authority and domain workflows stay in Rust. |
| A different backend language (Go, Java, Node.js, C#) for the control plane | §7.1's rationale (memory and thread safety without garbage-collector pauses in a long-running stateful service, strong state-machine types, one language across control plane and edge) is the report's recorded argument; the choice is nonetheless provisional with named revisit triggers (§25.1). |

## Consequences

**Positive.** One deployment to operate and secure in 0.x; transactional boundaries stay inside one database (§6.3); strict crate dependency rules keep future extraction mechanically possible; the modular-monolith boundary work is reusable if extraction happens later.

**Negative.** Scaling granularity is coarse until extraction; Rust hiring/depth is a real risk — it is a named §25.1 revisit trigger; internal discipline (crate boundaries, clippy gates per §22.2) is required to prevent the monolith from degenerating.

**Constrains later phases.** Crates are introduced only with real code, clear ownership, and a stable dependency direction (§8.1; AGENTS.md §1); §8.2 dependency rules are enforced in review and CI; the background worker process (§8.3 item 4) is split only if scheduling/ingestion workloads demonstrably require it.

## Revisit conditions

- §25.1 triggers: the team cannot sustain Rust depth, or a required protocol library has no adequate binding.
- A measured need per §8.3 (independent scaling, security isolation, runtime isolation, release cadence, fault containment) justifies extracting one service — extraction of individual services does not reopen the language choice.
