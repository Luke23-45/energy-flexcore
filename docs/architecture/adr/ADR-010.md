## Context

§13 opens: "Advanced AI is an extension layer, not a required dependency for safe baseline operation." §13.4 defines the research plugin boundary: research plugins may return a proposed schedule, candidate setpoint vector, ranking/score, forecast distribution, uncertainty estimate, or diagnostics — "They do not return an authorization token. The protected FlexCore validation and authorization path remains mandatory." §13.3 adds that a control-barrier-function or safety-projection layer must be derived from a valid system model and the correct relative degree, a filter can be infeasible, and "a finite test set with zero observed constraint violations is not a universal safety guarantee. Never allow a research MARL worker to issue live device commands." §5.7 makes `dispatch.authorize` never granted to general plugins; §17.5 invariant 7 states: no direct physical command from an optimizer, GNN, MARL, LLM, or general plugin — enforced by protected platform code. §0.3 lists "GNN or MARL outputs are safe by construction" among the non-promises.

Evidence: ledger/phase-00-product-freeze/19_plugin_model.md (P0.19 §4: no category may authorize, issue, or directly command; §7: permission table; §9: ADR alignment), with P0.17 and P0.11 freezing the supporting invariants.

## Decision

Outputs of ML/RL components — GNN, MARL, forecasters, optimizers, LLMs, and any research plugin — enter the platform only as proposals (schedules, candidate setpoints, rankings, forecasts, uncertainty, diagnostics) and must pass the same protected validation, feasibility, and authorization gates as every other candidate (§14). They never receive authorization tokens and cannot call device protocols directly; the deterministic baseline of ADR-009 remains the operational reference.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Allow ML/RL direct dispatch guarded only by a safety filter (e.g. control-barrier-function layer) | §13.3: the filter must be derived from a valid system model with the correct relative degree and can itself be infeasible; zero violations on a finite test set is not a universal safety guarantee; research MARL workers are never allowed live device commands. A filter is a mitigation inside the proposal path, not a substitute for the authorization gate. |
| Exclude ML/RL from the platform entirely | §13 makes advanced AI an extension layer with real value (candidate warm-starts, constraint prediction, research baselines); excluding it is unnecessary once outputs are structurally incapable of dispatch (§13.4) and would foreclose the §19.3/§19.4 research evaluation tracks. |
| Automatic promotion to dispatch authority after successful shadow evaluation | Promotion to any higher-authority mode requires the §22.3 release gates plus site-specific acceptance (§21.4); bounded automation is post-1.0, per deployment, site, and asset class after qualification (§2.1). No test-success count creates authority. |

## Consequences

**Positive.** Research and product development proceed in parallel without the research track touching the authority path; every ML/RL contribution is evaluated against the deterministic baseline (§13.3); the safety story reduces to a small, auditable kernel surface.

**Negative.** ML/RL value is capped at proposal quality until a fully qualified architecture exists; converting research outputs into gateable candidates adds integration work (contract versioning, diagnostics, provenance — the §14.3 invariant fields, including source subsystem and plugin/model version); research velocity is bounded by contract stability.

**Constrains later phases.** The `research-gnn` and `research-marl` profiles carry no dispatch authority and are not enabled in v0.1.0 (§5.8); every research output carries its source subsystem and model version into the command record (§14.3 invariant 3); console display must keep candidate and executed states visually distinct (§20.2); no plugin category includes a permit to authorize, issue, or directly command (P0.19 §4).

## Revisit conditions

- Granting any ML/RL output path direct or bounded-automation authority requires: a separate engineered and qualified architecture (§14.5 language), the §22.3 release gates, site-specific acceptance, and a new ADR superseding this one — post-1.0 only, per §2.1.
- Any change to §17.5 invariant 7 is an approved-design-decision event, not an implementation choice.
