## Context

§5.4 defines three execution classes: Class A (trusted built-in Rust modules, statically linked), Class B (sandboxed WebAssembly components with WIT interfaces, run under Wasmtime with explicit host-provided capabilities — no ambient filesystem, network, database, or secret access — and memory/fuel/time/output limits), and Class C (out-of-process gRPC/Protobuf workers for Python stacks, simulators, and components with large native dependencies). It then explicitly rejects arbitrary Rust dynamic-library (`.so`/`.dll`) loading for the 1.x line: the Rust native ABI has no stability guarantee ([R5]); a C-ABI wrapper could be designed but adds unsafe FFI, memory-ownership, versioning, and crash-isolation problems and is not the default extension mechanism. WASI 0.2 / the supported Component Model baseline is the first plugin SDK target; WASI 0.3 is not a release blocker at the 7 November 2026 cut-off ([R3]; `RESEARCH.md` §4). §25.1 carries the revisit trigger "component tooling is not stable enough for the v0.5.0 target".

Evidence: ledger/phase-00-product-freeze/19_plugin_model.md (P0.19 §5) freezes the three classes and the dylib rejection, and records the ledger risk that a dylib loader introduced for convenience contradicts the freeze.

## Decision

Third-party plugins execute only as sandboxed WASM components (WIT interfaces, Wasmtime host, explicit scoped capabilities and resource limits) or as out-of-process gRPC/Protobuf workers. Arbitrary Rust dylib loading is prohibited in the 1.x line. First-party extensions use statically linked Class A modules.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Arbitrary Rust dylib (`.so`/`.dll`) plugin loading | The Rust native ABI has no stability guarantee ([R5]): version skew between host and plugin is undetectable, and a crashing or malicious dylib shares the host process with the protected kernel — no sandbox, no crash isolation. |
| A C-ABI FFI wrapper as the default extension mechanism | §5.4: it adds unsafe FFI, memory-ownership, versioning, and crash-isolation problems and is explicitly not the default extension mechanism. |
| Static built-in modules only (no third-party extension mechanism at all) | Safest, but defeats the v0.5.0 plugin SDK deliverable (§2.1), the integrator/extensibility goal (§1.3), and the provider seams of §5.2; Class B/C exist deliberately to admit third-party code under control. |

## Consequences

**Positive.** Sandboxed third-party code with no ambient access and bounded resources; language-neutral extension surface; supply-chain controls (signatures, provenance, SBOMs, §9.3) attach naturally at component boundaries; a plugin crash cannot take down the control plane.

**Negative.** WASM toolchain maturity constrains what plugins can do (WASI 0.2 baseline; async/streaming additions await 0.3 stability, [R3]); per-call overhead and WIT/versioning discipline; two additional execution mechanisms to operate (plugin host as a separate process per §8.3).

**Constrains later phases.** The WASM plugin host ships enabled from v0.5.0 (§2.1; §5.8); every plugin needs a validated, versioned manifest (§5.5) with pre-activation dependency/capability checks; no hot-reload of safety or dispatch providers (§5.6); no plugin may self-upgrade or fetch executable code at runtime (§9.3).

## Revisit conditions

- §25.1 trigger: component tooling proves not stable enough for the v0.5.0 target (would delay/reshape Class B, not reintroduce dylibs).
- WASI 0.3 and Rust toolchain maturation ([R3]; re-evaluate after stable toolchain and host compatibility mature, §5.4) — expands Class B capability without changing this ADR.
- A formally engineered C-ABI plugin path could be introduced only by a new ADR with a security review.
