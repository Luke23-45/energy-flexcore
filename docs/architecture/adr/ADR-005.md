## Context

§5.1 states the design rule verbatim: "Everything that can safely vary is a plugin. Anything that defines safety, authority, tenant isolation, audit integrity, or command lifecycle is a protected platform invariant." §0.2 makes the same point as a core principle: safety invariants, authorization, tenant isolation, command lifecycle, audit, and final dispatch validation remain controlled by the platform kernel. §5.2 defines the capability seam (contract / provider / consumer separation — e.g. the scheduling module depends on an `Optimizer` contract, never on a concrete solver import); §5.3 enumerates the eleven plugin categories, none of which may authorize, issue, or directly command; §5.7 gives the permission model (a plugin may propose work; it must never grant itself authority — `dispatch.authorize` is never granted to general plugins, `dispatch.issue` is owned by the protected dispatch service under a signed authorization token); §5.8 composes plugins into named, reviewable profiles. The seam/profile ideas follow the documented DeepSeek Harness architecture — the ideas, not its implementation or maturity claims (§5.1, [R2]).

Evidence: ledger/phase-00-product-freeze/19_plugin_model.md (P0.19) freezes the protected-kernel rule, the seam rule, all eleven categories, the §5.7 permission table, and the profile table.

## Decision

Extension happens only at capability seams (contract/provider/consumer) composed through named, reviewable profiles. The protected kernel — safety invariants, authorization, tenant isolation, audit integrity, and command lifecycle — is non-replaceable platform code: no plugin can replace it, bypass it, or be granted `dispatch.authorize`; the kernel owns final authorization and dispatch state transitions (§0.2, §5.7).

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Make literally every module a plugin (maximal microkernel) | §5.1 explicitly rejects this: stable core contracts and security invariants must not be replaced by arbitrary extensions. It would put the §17.5 safety invariants behind swappable code. |
| A closed core with no third-party extension surface | Fails the product's open/modular goal (§0, §1.3 — system integrators need extensible interfaces) and removes the provider competition the seams are designed for (§5.2 worked example). |
| Safety and authorization policy as plugin-configurable settings | Contradicts §5.7 (plugins may propose, never self-authorize) and §17.5: the invariants are enforced by protected platform code and cannot be bypassed by plugins (P0.17 §6). |

## Consequences

**Positive.** Third-party innovation is possible without touching authority paths; every runtime composition is an explicit, reviewable profile (§5.8); the protected kernel is a small, auditable surface; supply-chain controls (§9.3: signatures, SBOMs, manifest validation) have a well-defined activation point.

**Negative.** Upfront contract design and versioning discipline (SemVer per contract, compatibility matrices, WIT versioning) is a continuing cost; some flexibility is permanently off the table; the seam boundary must be defended in review against "just one import" erosion.

**Constrains later phases.** No hot-reload of safety or dispatch providers in the 1.x line; activation/upgrade must not occur mid-dispatch (drain first, §5.6); v0.1.0 ships only static built-in providers and the `sim-lab` profile; the constrained WASM host is deferred to v0.5.0; a plugin can never select a control-authority mode (§21.4).

## Revisit conditions

- If a protected area demonstrably needs variation, that is a platform change requiring an approved design decision and a new ADR — never a plugin.
- Toolchain/execution mechanics (WASI maturity, host runtime) are revisited under ADR-006 and do not reopen the seam/protected-kernel model.
