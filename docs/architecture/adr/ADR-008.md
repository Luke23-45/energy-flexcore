## Context

§15.1 assigns the API styles: REST/JSON for the external management API (CRUD, queries, operator actions, plugin management) with a versioned base path (for example `/api/v1`) and published OpenAPI; gRPC/Protobuf for internal worker RPC, compute services, and edge service messages where appropriate; NATS subjects/JetStream for durable events and asynchronous work; WebSocket/SSE for live operator views; WIT for sandboxed WASM extension calls. §10.5 requires Protobuf for cross-process contracts and generated clients, with `buf lint` and `buf breaking` in CI, and forbids exposing raw database schemas as public API contracts. §15.2 lists the sixteen candidate REST resources and closes with: "Do not expose a generic 'execute arbitrary command' endpoint." §21.4 puts REST API, Protobuf schemas, plugin WIT interfaces, and plugin manifests under Semantic Versioning; the 0.x line may break contracts with a documented migration note; v1.0.0 freezes the public API and plugin contracts for the 1.x line.

Evidence: ledger/phase-00-product-freeze/15_api_surface.md (P0.15) freezes the five styles, the sixteen candidate resources, the versioning rules, the no-arbitrary-command-endpoint prohibition, and the no-raw-schema rule.

## Decision

Internal cross-process contracts (control plane to workers, compute services, and edge messages where appropriate) use Protobuf over gRPC, checked in CI with `buf lint` and `buf breaking` ([R17]). The external API is REST/JSON under a versioned base path with published OpenAPI. No generic "execute arbitrary command" endpoint exists; no raw database schema is exposed as a public contract; public contracts follow SemVer.

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| gRPC everywhere, including the external API | §15.1 assigns REST/JSON to external management; enterprise client integration breadth is the §25.1 rationale for REST/OpenAPI externally. gRPC externally would narrow the integrator audience (§1.3) that the external API exists for. |
| REST/JSON-only, internally too | Loses the strong typed contracts, generated clients, and schema-compatibility tooling that §10.5 requires for cross-process evolution; worker/edge contracts would drift without mechanical breaking-change detection. |
| GraphQL as the external style | Not chosen for the first build; §25.1 records it only as the named alternative should the client ecosystem demand another external style (revisit trigger). |
| Exposing database schemas as API contracts | Explicitly forbidden by §10.5; it would weld every external client to internal storage evolution (P0.15 §5). |

## Consequences

**Positive.** Mechanically checked internal contract evolution (Buf in CI, §22.2); a stable, documented, broadly consumable external surface; clean layering — contract types, not database rows, at every boundary.

**Negative.** Two contract systems and their generated code to maintain; OpenAPI and Protobuf descriptions must be governed so they do not drift apart; the candidate resource list needs deliberate revision discipline as the API grows.

**Constrains later phases.** All mutating dispatch routes are among the §15.2 resources (or documented revisions) — never a pass-through execute path (P0.15 §4); commands follow the frozen lifecycle (ADR-002 context; P0.11); the §21.4 SemVer scope (REST API, Protobuf schemas, WIT, manifests) applies; 0.x may break with a documented migration note; v1.0.0 freezes the public contracts for 1.x.

## Revisit conditions

- §25.1 trigger: the client ecosystem demands GraphQL or another external style — an external-style change only; the internal Protobuf decision is unaffected.
- The sixteen-resource candidate list can be revised by documented decision as domains mature (P0.15 freezes candidates, not final surface).
