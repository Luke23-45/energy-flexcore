## Context

§12.5 opens: "A candidate dispatch is not accepted merely because the optimizer reports success," and defines the eight-step validation pipeline that applies candidate injections to a **versioned network model**, runs the appropriate power-flow model, verifies limits, reports non-convergence and coverage gaps explicitly, and rejects/holds when the model is stale, incomplete, or the validator fails — a missing/uncertain/stale model is never interpreted as a passing feasibility check (§17.5 invariant 9). §12.3 defines the optimization tiers (Tier 1 LP/QP/MILP portfolio scheduling with linearized network/asset models first; Tier 4 nonlinear AC-OPF reserved for advanced research and validated use cases) and the solver-class discipline: HiGHS is LP/QP/MIP and must not be described as an SOCP solver; Clarabel supports continuous conic optimization including SOCP but not integer variables (not MISOCP); IPOPT solves nonlinear problems locally with no universal global-optimality guarantee (§7.4). §12.6 makes problem class, solver version, and grid-model version first-class fields of every optimization result. A SOCP relaxation on a radial feeder may be inexact and requires verification with an independent AC power-flow engine (§12.5).

Evidence: ledger/phase-00-product-freeze/12_grid_model_contract.md (P0.12) freezes the versioned-model rule, the SOCP-exactness rule, the failure rule, and the eight-step pipeline; ledger/phase-00-product-freeze/13_solver_class_discipline.md (P0.13) freezes the solver-class table, the four tiers, and the provider-contract declaration list.

## Decision

The first operational baseline is a deterministic optimizer (Tier 1 LP/QP/MILP portfolio scheduling with linearized network/asset models) whose every output candidate is independently validated against a versioned network model before any FEASIBLE transition. Optimizer success is never acceptance evidence; solver-class discipline is absolute at every seam; every result carries its declared problem class, solver/provider version, and grid-model version (§12.6).

## Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Accept optimizer output as feasible (single-stage) | Directly contradicted by §12.5's opening rule and §17.5 invariants 3 and 9; it would let linearization errors, stale models, and non-convergence reach the dispatch path silently. |
| SOCP relaxation alone as feasibility evidence | §12.5: a branch-flow SOCP relaxation may be inexact for reverse power flow, voltage upper bounds, and arbitrary network constraints; exactness must not be assumed, and an independent AC power-flow verification is part of the frozen feasibility evidence. |
| Nonlinear AC-OPF as the first operational baseline | §12.3 reserves Tier 4 for advanced planning/research and validated use cases; §0.3 makes "universal AC-OPF global optimality" a non-promise; AC-OPF as the default path would couple the first operational slice to the hardest, least predictable problem class. |

## Consequences

**Positive.** Reproducible, explainable decisions that can be replayed against the same model version (§24 step 10); a deterministic reference that research methods (GNN warm-starts, DMPC, MARL) are explicitly compared against (§13.3); benchmark-friendly (§19.3); solver-class mislabeling is mechanically checkable in review.

**Negative.** Two-stage optimization-then-validation costs compute and latency; linearized models can under- or over-estimate flexibility on constrained networks, requiring conservative margins; advanced solver capabilities (continuous SOCP, MISOCP/MINLP, AC-OPF) are deferred until a concrete validated need.

**Constrains later phases.** The grid-model provider is selected in Phase 4, gated on D3; until then the recommended default for 0.x simulation planning is balanced radial distribution feeders with pandapower as the primary power-flow provider — a recommendation, not a decision, and unbalanced three-phase modelling enters the track from v0.4.0 (§25.2 closing paragraph; P0.05 §3.2). Every solver provider must declare problem classes, constraint types, scaling, tolerances, warm-start support, licensing, determinism, and diagnostics (§7.4; P0.13 §4). Feasibility verdicts are simulation evidence within declared model scope and tolerances, not guarantees of field behaviour (P0.12 §9).

## Revisit conditions

- D3 closes (network class and fidelity decided): the provider selection and tier defaults are re-examined then; a pilot requiring unbalanced or meshed modelling is the named revisit trigger for the default (P0.05 §3.2).
- A concrete test case requiring an additional provider (§12.4 closing sentence) extends the toolset without reopening this ADR; changing the baseline itself requires a new ADR.
