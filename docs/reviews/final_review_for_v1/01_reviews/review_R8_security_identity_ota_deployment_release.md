- Recommendation: Add the strict parser as a small pure function beside `WebhookSigningKey` (or in the phase-13 module Agent A owns), vector-tested against record 08 §4's rejection classes, so the resolver composition consumes code, not prose. Small, additive, testable.

## 5. Release-readiness verdict for this area

The security and identity surfaces are in strong shape for a WRITTEN-UNRUN baseline: the deny.toml byte-identity claim verifies exactly; the suppression/audit/scanning configs are honest empty states rather than fake clears; the edge-agent identity/zero-touch/eSIM/attestation modules are fail-closed designs with named error vocabularies, injected clocks, no hardcoded material, and no claim that exceeds its evidence; the webhook signing core implements the designed scheme (constant-time HMAC verification, replay tolerance, rolling secrets) with published vectors; the backup/DR, chaos, k8s, GitOps, and load-test artifacts all hold their human gates and INERT/WRITTEN-UNRUN statuses without exception; and no certification, compliance, or signed-artifact claim anywhere in scope overstates its register. What must be fixed before release is concentrated at the seams between recorded work and the release artifact: the observability tree has no consumer and its compose-wiring handoff was silently dropped (FRV1-R8-001); the root README describes a repository that no longer exists (FRV1-R8-002); the repository still has no own license (FRV1-R8-003); and two phase-13 follow-ups (the `whsec_` strict parser and the webhook Postgres/HTTP/composition path) have no code and no open-item tracker (FRV1-R8-004/005), plus two hygiene items (FRV1-R8-006/008). None of these requires new architecture — each is a small, additive fix or a recorded decision — but all six P1s should be closed or explicitly recorded as human-gate inputs before any v1.0.0 publication.
