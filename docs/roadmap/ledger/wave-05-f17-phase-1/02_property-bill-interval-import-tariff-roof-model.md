# W5.02 — Property, bill/interval import, tariff selection, manual/optional roof model

Workstream: companion-repo work (separate identity/database — NOT FlexCore control-plane work)

- **Objective:** Define the F-17 property, bill/interval import, tariff selection and manual/optional roof model from design §9 and §11.4, including the optional Green Button integration.
- **Design trace:** Design §14 F-17 Phase 1; §9 model tables; §11.4 Green Button optional integration; §8.2 step 1
- **Inputs / prerequisites:** Design §9 model tables; §11.4; W5.01 scope; W4.07 tiers; W4.08 tariff model.
- **Steps:**
  1. Define the records from the §9 model tables in substance: HomePlan (consumer identity, project label, country/jurisdiction, lifecycle, creation date; separate consumer root, no FlexCore tenant ID); PropertyProfile (address separately protected, coordinates, property type, timezone, occupancy assumptions; exact address PII has a stricter access/logging policy than coarse coordinates); LoadProfile (monthly bills and/or interval series, meter source, timezone, interval duration, import/export, quality, completeness; bill-only and interval-measured profiles are separate quality tiers, with no invented hourly profile masquerading as measurement); RoofPlane (geometry/area, azimuth, tilt, usable area, obstruction/shading descriptors, source/provider, imagery quality/date; every roof value is provider-derived, user-declared or site-verified, never silently combined); TariffProfile (utility, customer class, currency, import rate, export compensation, TOU schedule, tiers, fixed charges, demand charges, minimum bill, taxes, net-metering/net-billing rules, valid dates, source; versioned by jurisdiction and effective dates, with unsupported tariff features causing a named limitation/refusal); PVSystemScenario (DC size, inverter AC size, module/array assumptions, tilt, azimuth, losses, degradation, optional bifacial/soiling parameters; engine/provider inputs and model version are retained with every run); BatteryScenario (usable energy, power, chemistry, round-trip efficiency, SOC range, reserve, warranty/degradation and replacement assumptions; usable capacity separate from nameplate capacity; no battery-only scenario without an appropriate tariff/use case); FinancialAssumptionSet (installed cost, itemized CAPEX, O&M, replacement, discount rate, escalation, incentives, taxes, financing; every cost/incentive has jurisdiction, currency, source and date; a user-entered quote overrides a generic estimate but is labelled); ScenarioRun (immutable input snapshot, tariff/weather/roof/engine/model versions, solver status, output digest, warnings and uncertainty; one run is one fixed set of inputs, and editing any assumption creates a new run); ConsentGrant (purpose, recipient, fields, expiry, revocation status, created-at; sharing is specific, revocable, logged and separate from general terms of service). PVSystemScenario and BatteryScenario are consumed by W5.03, FinancialAssumptionSet by W5.04, ScenarioRun by W5.05, ConsentGrant by W5.06; this subtask owns the record definitions.
  2. Define bill/interval import (upload bills or enter monthly consumption; where available, import interval data through a supported utility consent mechanism or user-uploaded CSV) and tariff selection (search available reviewed jurisdiction tariff profiles).
  3. Define the roof model (optional provider roof-plane data where coverage/quality is adequate, otherwise user-drawn/declared planes and obstructions, with source and imagery age shown).
  4. Define the Green Button integration as optional, not a global assumption: where a utility supports Green Button Connect My Data it can provide customer-authorized usage/billing data through the ESPI model, with the interval varying by the utility meter data capability; manual bill and CSV import remain necessary.
  5. Define the §8.2 step 1 property/location rules: explain why a precise address is needed if a roof imagery provider is called, and offer a manual location fallback (approximate coordinates or declared location) where the homeowner does not provide a precise address.
- **Deliverable / output:** A property/bill/tariff/roof model note with the §9 records, the import and tariff-selection flows, the roof model, and the optional Green Button integration.
- **Acceptance criteria / exit check:**
  - [ ] All ten §9 records are defined with their §9 design rules (HomePlan, PropertyProfile, RoofPlane, LoadProfile, TariffProfile, PVSystemScenario, BatteryScenario, FinancialAssumptionSet, ScenarioRun, ConsentGrant).
  - [ ] Bill/interval import and tariff selection are defined.
  - [ ] The manual/optional roof model is defined with source and imagery age shown.
  - [ ] Green Button is stated as optional, with manual bill and CSV import remaining necessary.
  - [ ] The §8.2 step 1 rules are stated (why a precise address is needed for a roof imagery provider; a manual location fallback is offered).
- **Owner role:** Product + numerical engineering
- **Dependencies:** W5.01, W4.07, W4.08
- **Verification method:** Records checked against the design §9 model tables; Green Button scope checked against §11.4.
- **Risks / failure modes:** Silently combining provider-derived and user-declared roof values, or presenting a bill-only profile as hourly. Mitigation: source labels and tier separation are mandatory.
