# P20.02 — Production-Shaped Synthetic Data Policy

Status: **POLICY — WRITTEN-UNRUN** (decision record:
`docs/phases-11-20/phase-20-deployment-architecture-scale/records/02_p20_02_load_test_plan.md`).
No fixture has been generated, no run has consumed any data set.

## 1. Synthetic only

Every identity, payload, and value used by a load run is generated by the
scripts in this tree with the `SYN-` prefix convention. No production data
enters a load run, ever. The entire 0.x line is simulation-only; the load
run's ceiling is the simulation ceiling — nothing here touches field
control or implies otherwise.

## 2. Production-SHAPED, not production-asserted

The fixture SHAPE (entity chain, tenant spread, payload structure, cadence
pattern) mirrors the recorded platform shapes so the load path exercises
the real code paths:

| Shape element | Derived from (consumed by citation) | Default in the scripts | Status |
|---|---|---|---|
| Entity chain (tenant → portfolio → site → asset → candidate → schedule) | `deploy/compose/smoke.sh` (the Stage-1 chain) plus the P3.21/P3.22 record shapes (`ledger/phase-03-*`, the §12.5/§12.6 pipeline) | one chain, seeded once | the chain is real API flow; defaults are ASSUMPTIONS |
| Tenant spread | The RLS/tenant-isolation surface (P1.12, migration 0002+ policy shape) | 8 tenants in the dev-auth fixture (`FLEXCORE_SEED_TENANTS`) | ASSUMPTION — operator-tunable |
| Market/program record volumes | P16.01 market records store, P16.07 price signal ingestion, P16.08 telemetry export pipelines (`docs/phases-11-20/phase-16-market-integration-settlement/records/`) | not seeded in the current legs (the ladder exercises the registry/schedule/dispatch-read surfaces; market volumes enter when a P16-surface leg is added — a NEW policy version) | ASSUMPTION |
| Telemetry cadence pattern | P14.11 MQTT/Sparkplug uplink shape and the P14 adapter cadence records (`docs/phases-11-20/phase-14-protocol-device-connectivity/records/`) | not seeded in the current legs (telemetry ingest is a worker/NATS path; an ingest leg is a NEW policy version with its own seed step) | ASSUMPTION |
| Dispatch payload structure | The §14.3 command fields and the P4.30 DTO shapes | dispatch records are OBSERVED (read-only), never generated | the READ-ONLY contract |

Every default above is operator-tunable via env; a shape assumption is
labeled ASSUMPTION and is never presented as a measured production
profile.

## 3. Versioned sets (anti-silent-growth)

Changing any shape element in §2 — entity chain, spread, cadence, payload
structure — is a **NEW version of this policy and of the seeding step**,
recorded as such (the `benchmarks/research-set-v1.json` anti-silent-growth
rule carried over). Two runs' results are comparable only within the same
policy version; the version travels in every capacity statement P20.01 §5
records.

## 4. Dev-auth boundary

The fixture is created with the dev-auth token shape (the `smoke.sh`
pattern): `Bearer dev tenant=<uuid> subject=<ref> role=platform-admin`.
Dev-auth is a TEST-LAB identity resolver — the load runs it enables are
simulation-only exercises; nothing in this policy implies a production
authentication posture (the P13 identity work owns that surface).

## 5. What this policy does NOT establish

1. No data set exists yet; no fixture has been generated.
2. No production-profile claim: every shape default is an ASSUMPTION.
3. No capacity implication: the data shape exists so the human run
   measures something reproducible; P20.01 owns what the numbers mean.
